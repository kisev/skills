# Canonical specification проекта

Поддерживай `specs/` как общий источник истины для человека и агентов. Документы
описывают согласованное состояние системы после merge, а Git хранит историю.

## Выбор режима

Пользователь должен явно передать один режим: `spec-init`, `spec-onboard`,
`spec-update` или `spec-audit`. Если режим не передан, остановись, кратко опиши
четыре режима и попроси выбрать. Не выбирай режим по догадке и не переходи к
реализации после specification workflow.

Читай только нужные ресурсы под собственным корнем skill:

- всегда: `references/requirements.md`, `references/architecture.md` и
  `references/interviewing.md`;
- для brownfield: `references/onboarding.md`;
- для ADR: `references/adr.md`;
- для `spec-update`: `references/consolidation.md`;
- для аудита: `references/auditing.md`.

Используй `templates/` как инструкцию по содержанию. Не копируй placeholders и
служебные подсказки в итоговую specification.

## Инварианты

- Canonical structure содержит все 19 обязательных `README.md` из
  `templates/specs/`. Пустой или неприменимый раздел кратко объясняет причину.
- Документы компактны, описывают целевое состояние в настоящем времени и не
  дублируют один факт в нескольких viewpoints.
- Текст документов на русском. Английский допустим в идентификаторах, путях,
  стабильных `REQ-*` и `ADR-*` ID, терминах глоссария и общепринятых технических
  терминах.
- Requirements и architecture организованы по типу знания, а не по feature,
  milestone или задаче. Machine-readable contract остаётся источником истины для
  синтаксиса; Markdown фиксирует семантику, ошибки, совместимость и инварианты.
- Дополнительные файлы допустимы только по semantic boundaries из справочника.
  ADR создавай только для архитектурно значимого решения.
- Не создавай roadmap, archive, proposal, delta, tasks, plan, research, analysis,
  mapping и другие постоянные артефакты процесса.

## Диалог и запись

Отделяй подтверждённые факты репозитория от намерения человека. При неоднозначности
по требованиям, внешнему поведению, архитектуре, совместимости, безопасности или
качеству используй штатный интерактивный механизм host; при его отсутствии задай
вопрос в чате. Не спрашивай то, что уже подтверждено.

В режимах записи сначала покажи точный diff создаваемых или изменяемых canonical
documents и получи подтверждение именно этого diff. До подтверждения ничего не
изменяй; после него применяй согласованный diff без новых смысловых изменений.
После записи покажи краткий итог и фактический Git diff, включая новые файлы, затем
остановись.

При выборе устойчивого дизайна в режимах записи разработай не менее двух
существенно разных вариантов, сравни их с ограничениями, интерфейсами,
отказами, совместимостью, безопасностью, наблюдаемостью, тестируемостью,
миграцией и откатом. Получи выбор человека. Архитектурно значимые альтернативы и
итог сохрани в ADR.

## Режимы

### `spec-init`

1. Убедись, что `specs/` отсутствует и проект действительно greenfield. Если уже
   есть значимые исходный код, тесты, схемы, конфигурация, CLI/API, CI или
   deployment, остановись и предложи `spec-onboard`.
2. Проведи адаптивное интервью по областям из `references/interviewing.md`.
3. Покажи preview полного `specs/`, получи подтверждение и создай все 19 файлов.
4. Не меняй код и не создавай план реализации.

### `spec-onboard`

1. Убедись, что `specs/` отсутствует. Иначе предложи `spec-update` или
   `spec-audit`.
2. Исследуй repository evidence по `references/onboarding.md` до вопросов.
3. Классифицируй отдельные утверждения как `KNOWN`, `AMBIGUOUS`, `UNKNOWN` или
   `CONFLICT`. Не выдавай текущее поведение кода за поддерживаемый контракт.
4. После интервью покажи preview и создай только canonical `specs/` и необходимые
   ADR.

### `spec-update`

1. Убедись, что `specs/` существует, прочитай затронутую область и согласуй
   желаемое изменение.
2. До проектирования обязательно выполни анализ из
   `references/consolidation.md`. В preview явно включи `Consolidation: required`
   с точными упрощениями или `Consolidation: not required` с причиной.
3. Согласуй однозначное целевое состояние. Новое существенное требование получает
   новый ID; существующие ID не перенумеровывай и не переиспользуй.
4. После подтверждения изменяй только `specs/`, включая ADR внутри
   `specs/architecture/09-architecture-decisions/`.

### `spec-audit`

Этот режим полностью read-only. Без аргумента проверь все `specs/`; с путём,
`REQ-*`, `ADR-*` или областью проверь заданный объект и связанные evidence.
Следуй `references/auditing.md`: сначала выведи ранжированные замечания качества,
затем статусы drift и непроверенные границы. Не создавай отчёты, ADR и временные
артефакты, не предлагай автоматически применить исправление.
