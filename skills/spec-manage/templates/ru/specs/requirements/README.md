# Требования

## Назначение

Объясните, что этот раздел содержит нормативные, проверяемые соглашения о поведении системы, интерфейсах, качестве и ограничениях.

## Включено

- Индекс четырех типов требований.
- Общие правила монотонной нумерации стабильных ID, истории жизненного цикла и прослеживаемости.
- Взаимоисключающее семантическое владение для четырех типов требований.
- Ссылки на машиночитаемые контракты.

## Исключено

- Структура компонентов и потоки выполнения, планы реализации, декомпозиция задач или повторение дочерних требований.

## Правила декомпозиции

Используйте только четыре обязательных каталога типов. Не создавайте новые типы верхнего уровня.

## Ожидаемая структура

```text
requirements/
├── README.md
├── functional/README.md
├── interfaces/README.md
├── quality/README.md
└── constraints/README.md
```

## Шаблон содержания

Дайте краткий индекс разделов. Укажите, что `REQ-F-*` владеет наблюдаемым поведением, не зависящим от транспорта, `REQ-I-*` - внешней поверхностью и семантикой протокола, `REQ-Q-*` - измеримым или проверяемым качеством, а `REQ-C-*` - внешне заданными ограничениями решений. У одного нормативного факта один владелец; остальные документы ссылаются на него. Укажите, что новые номера выше исторического максимума, активным требованиям не нужен шаблонный статус, а неактивные используют компактную строку ниже. Удалите эти инструкции из созданного документа.

```markdown
> Lifecycle: `superseded` | Changed: `YYYY-MM-DD` | Reason: <причина> | Replacement: [REQ-X-NNN](#replacement-heading)
```

Используйте только `deprecated`, `superseded` или `withdrawn`. Дата и причина обязательны; ссылка на замену обязательна для `superseded`, запрещена для `withdrawn` и добавляется для `deprecated` только при наличии замены. Разрешены переходы из активного состояния в любое неактивное и из `deprecated` в `superseded` или `withdrawn`; терминальные записи не активируются повторно.
