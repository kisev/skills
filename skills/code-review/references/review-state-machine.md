# Guided remote review

The agent owns analysis; `reviewmatic` owns collection, bindings, validation, freshness, verdict derivation, finalization. Use the guided commands below; never reconstruct transitions or inspect the runtime source.

## One editable draft

1. Run `reviewmatic start-review --url MR_URL --review-mode MODE --locale LOCALE --incremental INCREMENTAL` (modes `fast|normal`, locales `en|ru`, incremental `auto|off`) with `--repo-root CHECKOUT`: the runner verifies its exact base/head objects (instructive error otherwise) — it never clones a repository for the MR. It prepares a managed review worktree at the exact MR head — `review_worktree`, with source repository and exact base/start/head/target refs — where critics read all code. Inspect evidence, context, `inspection_path`: the index holds the complete diff and exact base/head source snapshots, never working-tree files; missing, binary, non-regular, and over-budget snapshots explicit. Never duplicate MR collection with `glab mr view`. Read `draft_schema_path`, `input_contract`, and `input_examples` immediately. Complete and record the returned context package template before critics launch; assigned questions are answered by critics in `question_answers` and every `not_verified` answer is checked by the primary in `question_verifications` — see `references/context-package.md`.
2. Record the panel with the returned `record-participants` action. Review code and discussions only as orchestration requires. Fill the returned `draft_path` identity fields (`run_id`, `session_id`, `low_risk`) via `record-input`; findings, dispositions, CI assessments, and content sections arrive only via the arbitration receipt. Each disposition: `id`, `decision=accept|reject`, `reason`, `dependencies` (`paths`, `thread_ids`, `metadata_fields`, `ci`) — accepted candidates may use empty lists, rejected ones concrete scope dependencies. Preserve receipt identities and distinct finding ID prefixes per critic; `severity_override` records `original_severity`/`severity`/reason, `duplicate_of` names the canonical finding, and `existing_thread` fix records bind `thread_id` without dropping the defect from readiness. Complete each generated `ci_job_assessments` entry from its bounded trace: `trace_evidence` is an exact non-empty substring of the collected redacted trace, project/pipeline/job IDs preserved.
3. The arbitration receipt completes `content`: semantic chat/architecture/metadata/SemVer assessments, every catalog label, checks, concrete `finding_publications`, previous-finding assessments, recommended issues, thread decisions. Metadata input: the flat five-field assessment, not an `observed` wrapper. Publication input: exactly `finding_id`, `type`, `path`, `line`, `old_line`, `body`, `fix_mode`, `patch`; optional `suggestions`/`split_rationale`/`patch_reason` (mandatory for fallback). The runner derives findings, candidates, revisions, paths, digests, verdicts — never add derived fields or copy data between artifacts. Grouped thread suggestions may carry prose-only `routing_response` for a new-position reply, never replacing the shared explanation or parts.
4. Run the returned `reviewmatic check-review --draft DRAFT_PATH`: it validates locally without GitLab reads, publication artifacts, or progress changes; fix the reported fields and repeat.
5. Run the returned `reviewmatic finish-review --draft DRAFT_PATH`: local revalidation (no GitLab request at finalization), then atomic publication of plan, Markdown, and baseline. An explicit `refresh-review` and the head check guarding every manual publication block catch post-review drift. Print `chat` verbatim and one fenced `plan_command`; never run a publication command during the review.

After interruption, `reviewmatic resume-review --artifact-root ROOT` returns the same editable draft, participants, and pending panel steps without recollection. `reviewmatic refresh-review --draft DRAFT` refreshes changed evidence, retaining the selection; old plan and draft are preserved. Finalized new plans use `repair-review` (`references/repair.md`). Collection, validation, and finalization timings are separate from model and subagent time; never blame review analysis on the runtime or hide validation-repair loops.

## Review panel: critics and arbitrator

The panel matches the run path and `references/review-panel.md`: one recorded selection (`reviewmatic record-participants --draft DRAFT --input participants.json`: critics plus arbitrator), then parallel independent critics, then one separate arbitrator. Ground the pool in the host's agent inventory before composing options (`review-panel.md`); set the critic count through the selection itself, fixed once receipts exist. Import each critic receipt via `reviewmatic record-critic --draft <draft-path> --input <receipt>` with its exact `--participant` name; the runtime binds receipt identity to the participant, rejecting re-use. Each critic performs one complete independent review: findings plus answers to its assigned questions, from the same package and snapshots, without other critics' output, GitLab recollection, or file-map rebuild. Every finding traces its symptom to the changed lines through concrete code (symptom-path tracing), and unreachable-code claims prove unreachability from a real entrypoint.

Absence of `critic` is not a blocker. Supply the recorded context package path, exact snapshot paths, materialized `references/simplification-criteria.md` path, accepted scope, user decisions — never another reviewer's conclusions. Reading the package as primary context, the critic answers each assigned question with one verdict — `confirmed`, `refuted`, or `not_verified` — plus evidence or a concrete reason bound to that question's `context_digest`; with several critics, the runtime enforces the pair rule (one critic's answer never covers another's assignment). Edited-question re-records retire affected answers into `superseded_question_results`; late superseded-bound receipts are refused (`references/context-package.md` owns the arithmetic). Request complete detailed findings in the required report envelope (`review_report` is valid for routed specialists); populate the returned receipt template: its `run_id` is pre-stamped with this run's identity (keep it), and `session_id` is the critic subagent's real native session id, never a copied or invented label. Never ask a child to guess its identity, switch providers, invent an identity, fabricate a receipt, or run `opencode run` to evade a failed delegation policy; if the host cannot launch any independent native subagent of the current agent, report that capability failure before an extended review instead of weakening depth, and never replace or omit a failed specialist without reconciling the selected critic count.

Once the last critic receipt is imported, the arbitrator task arrives with the same package binding, every receipt verbatim, and the reported contradictions; its duties, ladder, import, and refusal contract live unchanged in `references/review-panel.md`.

## Compatibility and verdict

Existing v2 artifacts and low-level commands (`prepare`, `context`, `template-review`, `record-artifact`, `finalize`, `finalize-review`, `scaffold-review`, `status`, `report-review`) stay supported for old callers; never mixing them with a guided draft; progress stages stay inspectable.

Every accepted non-low finding blocks `ready`; failed or canceled CI jobs require trace-supported classification across child/downstream pipelines, with only proven manual process gates non-blocking and missing, active, stale, incomplete, unknown, or unclassified CI evidence staying blocking. Every previous finding and critic candidate needs an explicit arbitrator verdict; generated verdicts never replace the arbitrator's semantic assessment or authorize publication.
