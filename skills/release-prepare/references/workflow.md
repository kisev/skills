# Release preparation

Read `references/interaction-contract.md`, `references/gitlab-workflow.md`, `references/portable-gitlab-contracts-v2.md`, `references/label-semantics.md`, `references/language-policy.md`, and `references/release-examples.md`. Accept exactly one release MR URL; do not infer it from a branch or prepare a batch. The skill and every helper are read-only for GitLab: they may collect evidence and write local artifacts, but they never execute a publication command.

## Evidence and inventory

Treat `diff_refs.head_sha` as the release head and verify that the local checkout resolves it exactly. The release MR source branch is the component MR target branch. Select the nearest stable SemVer `v*` tag at or above `v1.0.0` on the first-parent ancestry, skipping prerelease, build-metadata, pre-1.0, and non-SemVer `v*` tags, or use an explicitly confirmed stable SemVer tag at or above `v1.0.0` or full 40-hex commit SHA. Resolve an explicit tag only as the peeled commit of the exact local `refs/tags/<name>` ref, and resolve an explicit SHA to that exact local commit; never accept a branch, short SHA, `HEAD` expression, prerelease, or build-metadata tag. Verify ancestry, include the root commit when no tag exists, and never select by tag creation date or fetch implicitly.

Create the inventory with `scripts/prepare_release.py inventory --evidence <evidence-path> --repo-root <checkout>`. Add `--previous-ref <stable-tag-or-full-sha>` only for an explicit boundary. Preserve that exact tag or SHA as `previous_ref`. Resolve every release commit and all associated component MRs with complete pagination. Any unresolved range, association error, truncation, or incomplete MR, discussion, approval, note, pipeline, or work-item evidence makes the inventory incomplete.

Verify each release item against MR text, commit subject and body, diff, discussions, and explicitly linked work items. Work-item candidates are bounded to items linked or referenced by the release MR, component MRs, and commits in the exact inventory; do not search the project for more. For every candidate, record `close`, `comment`, or `no action`, with its evidence-based rationale and any uncertainty. Do not ask work-item questions: make uncertainty prominent and let the user skip any manual command they reject.

Contributors are all authors of non-merge commits in the release range. Reviewers are people who approved or participated in a discussion or note on any component MR; exclude bots and system events. Deduplicate each list by verified GitLab identity, then normalized email or name, without guessing identities. Present both final lists for interactive user approval before finalizing the runbook.

## Decisions and content

Choose MAJOR, MINOR, or PATCH from observable compatibility, configuration, schema, API, default, migration, and deprecation changes. Present the rationale and obtain the user's version decision. For a `v*` boundary, the selected version must be the exact next stable SemVer bump and must match the selected compatibility impact. A SHA boundary has no implied prior version: require an independently confirmed stable version at or above `1.0.0` and compatibility impact rather than treating it as a first release or forcing MAJOR. Prerelease, build metadata, and pre-1.0 versions fail closed; without a previous boundary, only `1.0.0` with MAJOR impact is valid. Recommend a milestone from the release MR, component MRs, and complete project milestone catalog, then ask the user to select it or `Custom`; the custom option accepts another existing milestone or a new milestone definition. Normalize versions without a duplicate `v` prefix.

Preserve the current release MR description structure when it remains usable. Otherwise use the applicable local project release/MR template from the exact checkout, and use the built-in structure from `references/release-examples.md` only when neither is usable. Prepare the title, description, and announcement in the language of the latest user request; use English when that language is ambiguous. Apply `humanize` to the title, description, and announcement prose. Every release item states the change, impact, required action, and source `!IID` or linked 7-character commit SHA. Keep compatibility and migration even when no action is required. The announcement contains 3-5 concise outcomes.

Ask the user to choose `Pixel-art release quest`, `Literary world`, `Neutral abstract systems`, or `Custom` for the illustration. If they choose `Literary world`, ask the mandatory follow-up for the book or series; if they choose `Custom`, ask for the intended style. Prepare an English 16:9 prompt grounded in one to three concrete inventory changes, without text, letters, numbers, code, logos, interfaces, or invented claims.

Report `success`, `running`, `failed`, `canceled`, or `missing` only for a pipeline whose SHA equals the release head. Mention success only when confirmed. Set semantic `change_type=release` and the confirmed `compatibility` impact; use no concrete label names and leave unsupported roles `null`.

## Stable runbook

Atomically replace one target-scoped `release-publication.md` only after the evidence and decisions are complete. Keep immutable payload and body files behind it, retain changed body-only versions, and list only earlier version paths at the end of the current runbook. The pre-merge section contains exact previews and direct manual `glab` commands, in order, to create the selected new milestone when needed, update the release MR and milestone, post an MR comment containing the announcement and an attachment for the illustration prompt, and merge the MR. Omit inapplicable commands rather than placeholders. Every command consumes the immutable payload shown in the runbook and binds the exact host, project, MR IID, release head, selected milestone, and content; changed bindings require regeneration. Each mutation records an advisory XDG marker after exit zero, but the marker is not a GitLab postcondition or retry authorization. State prominently that no command was executed.

Regenerated mutation blocks expose `execution-status=not_run` or
`execution-status=run_unverified`. Keep the latter action visible until refreshed
GitLab evidence confirms its target state.

After the MR is merged, a separately invoked read-only post-merge helper refreshes this same stable runbook rather than creating another plan. It verifies the exact merged MR and commit, rejects an existing release or a same-name tag at another commit, copies the MR description byte-for-byte as the GitLab Release notes, and adds an exact manual `glab` release command plus one exact command for every approved work-item `close` or `comment` action. The same helper may refresh a stale post-merge runbook; when inventory changed, regenerate the approved content ledger and pass it with `--content`. Keep `no action` entries and all rationales and uncertainties visible. The helper never executes these commands or any other remote mutation.

Immediately before reporting either phase ready, finalize against the runbook's exact binding. Changed exact base/start/head SHA, MR or merge state, selected milestone, inventory, component MR evidence, contributor/reviewer approval, item decisions, payload, or artifact makes it stale. Report only the absolute stable runbook path; never create or update a milestone, MR, comment, attachment, label, merge, release, or work item automatically.
