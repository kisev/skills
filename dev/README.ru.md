# Dev-окружение

[English](README.md)

Корневой `docker-compose.yml` описывает один постоянный проект `skills-dev`:
GitLab CE `18.11.11-ce.0`, Runner `v18.11.0`, Mattermost `10.10.3`, PostgreSQL
и localhost HTTPS-прокси. Это инфраструктура разработки, не поставляемое
приложение и не переносимый навык. Нужны Linux, Docker Engine и Compose v2
с поддержкой `down` для выбранных сервисов. Сначала выполни `mise install`.

## Запуск и управление

```sh
task env:up
task env:status
task env:logs
task env:stop
task env:up
```

Каждая `env:<operation>` объединяет `env:gitlab:<operation>` и
`env:mattermost:<operation>` через `deps` Taskfile. Сервисная задача управляет
только выбранным сервисом и его зависимостями. По умолчанию используется
`docker-compose`; для CLI-плагина передай `COMPOSE="docker compose"`.

| Операция | Результат |
| - | - |
| `up` | Запуск, ожидание готовности, идемпотентная подготовка недостающих тестовых аккаунтов и данных |
| `stop` | Остановка; контейнеры, сети и данные сохраняются |
| `down` | Удаление выбранных контейнеров и свободных сетей проекта; данные сохраняются |
| `restart` | Рестарт выбранных контейнеров, ожидание готовности и подготовка fixtures |
| `recreate` | Пересоздание выбранных контейнеров и подготовка fixtures; данные сохраняются |
| `clean` | Удаление выбранных контейнеров, volumes и приватного состояния fixtures/навыков, включая личные данные; отчёты сохраняются |
| `status` | Состояние выбранных контейнеров, включая остановленные |
| `logs` | Последние 100 строк логов, без постоянного ожидания новых строк |

**`clean` удаляет данные сразу, без вопроса, preview и подтверждения digest.**
Например, `task env:gitlab:clean` удаляет и личные проекты GitLab;
`task env:clean` удаляет данные обоих сервисов. После очистки выполни `up`
для подготовки с нуля. Для сохранения данных используй `recreate`.

GitLab доступен на `https://localhost`, Mattermost на `https://localhost:8443`.
При смене портов сохраняй `GL_TEST_PORT` или `MM_TEST_PORT` для всех команд.
Полные GitLab workflows требуют порт 443: закреплённый glab отвергает порт
в `--hostname`. `MM_TEST_IMAGE` позволяет выбрать другую доступную патч-версию
Mattermost; не понижай версию уже мигрированной базы. Патч по умолчанию
не доказывает совместимость с непроверенной патч-версией рабочего сервера.

## Существующие данные и сертификаты

Первый `up` проверяет принадлежность прежних проектов по умолчанию, останавливает
и удаляет только их контейнеры и подключает существующие именованные volumes.
Содержимое volumes не копируется, не обходится и не очищается. Чужие ресурсы
отклоняются. Старые disposable-проекты не подключаются и не удаляются.
Credentials и отчёты сохраняются в `.build/gitlab-test/gitlab-workflows/`
и `.build/mattermost-test/mattermost-cards/`. Исторические имена каталогов
оставлены для совместимости, а не для создания отдельных окружений.

`.build/env/volumes.json` хранит выбранные volumes;
`.build/env/compose.env` передаёт их имена корневому Compose. Эти игнорируемые
файлы не содержат API credentials. Сохраняй их, пока нужны данные сервера.
Небольшой helper `dev/env.py` отвечает за подключение старых volumes, проверку
принадлежности, подготовку fixtures и ограниченную очистку; команды lifecycle
Compose выполняет Taskfile.

После подготовки прямая диагностика Compose выглядит так:

```sh
docker compose -p skills-dev --env-file .build/env/compose.env ps -a
```

HTTPS доступен только через loopback хоста. У каждого proxy собственный CA;
системное доверие и рабочие credentials не меняются. Публичные сертификаты
находятся в соответствующем `state/root.crt`, API credentials - в приватном
`state/fixtures.json`. Не передавай этот файл другим. Браузерные проверки
используют отдельные сессии и проверенные ключи сертификатов. У Runner нет
Docker socket хоста. PostgreSQL не имеет порта на хосте и использует локальный
trust во внутренней сети.

## Проверки и восстановление

```sh
mise exec -- agent-browser install
task test:integration:gitlab
task test:integration:mattermost
```

Тестам нужны уже запущенные и подготовленные сервисы. Они не запускают
и не останавливают контейнеры и не создают аккаунты. Публикации ограничены
fixtures; GitLab `manual` и Mattermost `free` не читаются и не сравниваются.
Git/glab/XDG не затрагивают рабочие установки: это изоляция состояния процессов,
а не ещё одно серверное окружение. Обычный `task check` не требует сервера
или провайдера. Охват, браузерные prerequisites, отчёты и опциональный live
описаны в гайдах [GitLab](../tests/integration/gitlab/README.ru.md)
и [Mattermost](../tests/integration/mattermost/README.ru.md).

`task test:integration:lifecycle` отдельно прерывает оба сервиса, чтобы проверить
down/up, recreate и повторный up по snapshots fixtures в этом же окружении.
Он не вызывает clean и не создаёт другой стенд; не запускай его во время
ручной работы. Отчёты находятся в `.build/env/reports/`. Безопасность очистки
проверяется offline, без удаления данных работающего окружения.

При ошибке запуска изучи `env:<service>:status` и `env:<service>:logs`, исправь
причину и повтори `up`; не используй `clean` лишь ради прохождения теста.
GitLab readiness ждёт startup post-reconfigure hook, затем проверяет Puma
и зависимости: отложенный рестарт Workhorse не пересекается с fixture-проверками.
При ошибке принадлежности нужно разрешить конфликт ресурсов, а не перехватывать
контейнеры или volumes другого checkout.
