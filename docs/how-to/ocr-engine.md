# Run the OpenCodeReview Engine

[Русский](../ru/how-to/ocr-engine.md)

The OpenCodeReview CLI (`ocr`) is the only review engine of `mr-review`. It
reads the diff, sends it to a configured LLM, and returns findings as JSON. The
skill never runs an in-house critic or an arbitrator.

## Install and pin the version

The minimum tested version is 1.13.6. Install or upgrade it with:

```shell
npm install -g @alibaba-group/open-code-review@latest
```

The skill's `references/requirements.json` carries the same install command as
its `ocr` entry, together with the check command `ocr version`. When the
installed version is lower, the runtime stops with the upgrade instruction.

## Select reviewers

Define aliases in `~/.reviewmatic/reviewers.json` globally and in
`./.reviewmatic/reviewers.json` locally; the local file overlays the global one
by alias and default:

```json
{
  "default": "fast",
  "reviewers": [
    {"alias": "fast", "provider": "openai", "model": "gpt-5", "effort": "medium"},
    {"alias": "deep", "provider": "anthropic", "model": "claude-opus-5", "effort": "high"}
  ]
}
```

Only `alias`, `provider`, `model`, and `effort` are allowed; never write a
credential into the profile. Read the effective profile and its provider
validation with `reviewmatic profiles`. The validation checks provider names
against `ocr llm providers`; custom providers are configured only in OCR's own
configuration, which the skill never reads.

Without a profile, use OCR's configured default or a one-off provider and model.

## Author the background

The manager writes the task goal, acceptance criteria, constraints, open
questions, and context sections as JSON and lets the runtime fit them into the
8000-byte limit:

```shell
reviewmatic background --input .reviewmatic/background.json --output .reviewmatic/background.md
```

The task comes first. Every section the limit cuts is listed in the printed
result, and the executed file is the measured one.

## Run and merge

```shell
reviewmatic ocr-runs --repo <checkout> --from <start-sha> --to <head-sha> --background .reviewmatic/background.md --reviewers fast,deep --output-dir .reviewmatic/ocr
```

Each alias runs its own `ocr review` process with its own output; several
aliases run in parallel. A one-off run uses `--provider` and `--model` instead
of `--reviewers`. A failed run is reported with its exit code and stops the
review; the manager never substitutes its own review.

When several runs were selected, the manager merges duplicates and conflicts
and records every reason. A finding is never dropped silently.

## Sessions and incrementality

Every run persists a session. A follow-up review is a fresh run plus:

```shell
reviewmatic ocr-compare --before <previous-session> --after <current-session> --repo <checkout>
```

The comparison groups findings as new, persisting, resolved, or not reviewed.
The grouping is advisory runbook context; the verdict stands on the current
run. `ocr review --resume <session-id>` continues an interrupted run.

## Publication

The runbook ends with one non-interactive draft-note block generated by
`reviewmatic drafts`. It starts with a head check against the reviewed head and
creates GitLab draft notes only. The human edits and publishes them in the
GitLab UI; no publish command exists.
