## Текущий выпуск

Поддерживаемый источник переносимых навыков - стабильный канал GitHub Pages:
`https://kisev.github.io/skills`; необязательный пакет -
`@kisev/agentomatic`. Для установки переносимых навыков используется
`npx --yes skills@latest`. Пакет требует Node.js 22.13+ и объявляет совместимость с
OpenCode `>=2.0.0 <2.1.0`.

## Установка переносимых навыков

Глобальная установка выполняется командой:

```shell
# Registry version of the installer
npm view --prefer-online skills@latest version

# Install skills
npx --yes skills@latest add https://kisev.github.io/skills --skill '*' --global --yes

# Installed skills
npx --yes skills@latest list --global
```

Тег npm может сдвинуться между командами. npx не устанавливает CLI глобально;
команда списка проверяет локальные навыки, а не версию npm или выпуска Pages.

Команда создаёт один основной экземпляр в `~/.agents/skills` для всех сред,
читающих `.agents/skills`, и других обнаруженных установленных сред. Без
`--global` экземпляр проекта находится в `.agents/skills`. Метаданные выпуска
указывают происхождение исходников; исходный репозиторий не используется для
установки.

URL Pages служит обновляемым каналом стабильных выпусков. `update` проверяет
текущую эталонную контрольную сумму, загружает изменённые архивы и предлагает
удалить отслеживаемые имена, удалённые в источнике. Для существующих установок из
Git нужно повторить `add` с URL Pages и той же областью, чтобы
сменить источник. Явная очистка ограничена устаревшими именами из текущего
[инвентаря миграции](migration-inventory.md).

## Интеграция OpenCode

Переносимые навыки не зависят от npm-пакета, а npm-пакет не устанавливает
переносимые навыки. Интеграция проекта постоянно хранится в его `node_modules`, а
глобальная интеграция - в npm-проекте `~/.config/opencode`.

Команды с областью по умолчанию работают с текущим каталогом и принимают один
`--global` для глобального состояния; параметр `--scope` не поддерживается.
Установщику необходимы предварительный просмотр и подтверждение. После
подтверждения он записывает выбранные компоненты, модели и критиков, а также
может подключить или отключить core и применить пресеты. `configure integration` -
подтверждённый путь для пользовательской конфигурации: она вливает выбранные
фрагменты в `opencode.json(c)` с нативными V2 `plugins`/`permissions` и в
глобальный `cli.json`, а для Kilo и MiMo - в `kilo.json(c)` и
`mimocode.json(c)`, по квитанции предварительного просмотра и подтверждения,
сохраняя комментарии, посторонние ключи и порядок пользовательских правил,
переводя только затронутые устаревшие разделы и сообщая о неоднозначностях как
о конфликтах; Kilo/MiMo расширяют скалярные карты разрешений с сохранением
исходного значения записью `"*"`. Обновление состоит из установки
точной версии через npm, предварительного просмотра `install`, точного
подтверждения и перезапуска OpenCode.

План uninstall показывает компоненты, отключение плагина, сохранение моделей и
явно выбранное удаление npm-зависимости. При ошибке npm завершённые локальные
этапы сохраняются. `maintenance cleanup` и `uninstall` архивируют
компоненты пакета с точно подтверждённой принадлежностью. Cleanup игнорирует
каталоги переносимых навыков и lock-файлы установщика; этим жизненным циклом
управляют `skills update/remove`. Конфликты, рабочие деревья и состояние
выполнения сохраняются; команд `restore` или `purge` для архива нет.

## Приложение reviewmatic на Python

`apps/reviewmatic` содержит единственный рантайм reviewmatic. Он обрабатывает GitLab
MR, локальный WIP, панель/арбитраж, инкрементальное ревью, ремонт и refresh,
приватное состояние XDG, управляемые worktree и прямые ручные runbook. Запуск
выполняется из выбранного Git-ref через `uvx`; npm и PyPI-рантаймов и TUI нет.
См. [руководство приложения](../../apps/reviewmatic/README.ru.md): выбор stable/dev
ref, обновление кэша и восстановление runbook.

Переносимое ядро `src/reviewmatic/portable/` материализуется байт-в-байт из
`shared/references/` через `pythonRuntime` в `shared/manifest.json`. 33 golden-
кейса сохраняют ожидания TypeScript-ревизии
`3e409c217e94d643f77eb543caab9a2ed4b7288d`; старое приложение и генератор
удалены. Python-тесты пересчитывают и проверяют каждый дайджест, вердикт и
переход состояния, не генерируя ожидания из самого Python. Исторический
TypeScript-baseline и карта соответствий приведены в
[матрице тестов](../reviewmatic-test-matrix.md).

```shell
task generate:check
task reviewmatic:check
task reviewmatic:install-smoke
```

`generate:check` проверяет материализованные общие источники и сохранённые
golden-утверждения. Гейт приложения запускает pytest, mypy, проверку lock-файла
и сборку wheel/source distribution. Отдельная install-smoke проверяет локальный
Git-ref и оба собранных дистрибутива вне checkout без Node, `PYTHONPATH` и
установленного инструмента `reviewmatic`. Smoke входит в области гейтов как
отдельный слой: CI и pre-push исполняют его при изменениях в
`apps/reviewmatic/**`, полный `task check` тоже включает его.

## shopmatic

Приложение shopmatic в `apps/shopmatic` — MCP stdio-сервер покупательского
поиска по маркетплейсам через закреплённый CLI `agent-browser`
([ADR-0020](../../specs/architecture/09-architecture-decisions/0020-drive-marketplace-storefronts-through-agent-browser.md)).
Его автоматический гейт полностью офлайновый: скриптованный фейковый
исполняемый файл `agent-browser` подменяет драйвер браузера, поэтому ни
тесты, ни гейт не обращаются к маркетплейсам:

```shell
task shopmatic:check
```

Гейт запускает `uv lock --check`, офлайн-набор тестов, локальные строгие mypy
и ruff, сборку uv и контракт версии CLI. Слой приложения зарегистрирован в
`gate-registry.json`, поэтому точечные записи CI-матрицы и pre-push-глобы
покрывают дельту `apps/shopmatic`.

Живая проверка витрин — ручной прогон, а не гейт, потому что она зависит от
внешних сайтов и репутации сети. Она повторяет приёмочные доказательства от
2026-10-05: анонимные прогоны на Wildberries и Яндекс Маркете должны открыть
поиск с ценовым потолком, дождаться рендера SPA и напечатать
структурированные результаты (название, цена, URL, рейтинг) из профиля,
пустота которого доказана до первой навигации; Ozon ожидаемо отвечает
антибот-челленджем и остаётся заблокированным. Повторите сценарий вручную:

```shell
uv run --locked shopmatic search wildberries "клавиатура" --max-price 5000 --limit 5
uv run --locked shopmatic search yandex-market "клавиатура" --max-price 5000 --limit 5
uv run --locked shopmatic compare "клавиатура" --limit 3
```

Селекторы маркетплейсов устаревают при редизайнах витрин; неисправный
адаптер отвечает явной ошибкой, а стоп-условия спайка в ADR определяют,
приостанавливается ли поддержка, а не обходится.

## Потребительский смоук

Гейты npm проверяют сборку и упаковку пакетов, но доказать, что опубликованный
тарболл реально ставится и типизируется, может только настоящий потребитель.
Гейт потребительского смоука выводит набор публикуемых пакетов программно из
корневого `package.json` (workspaces с `private != true`), упаковывает его после
`package:build` и ставит свежие тарболлы в один временный consumer-проект:
сначала пакет-фундамент без зависимостей от других workspaces, затем все
зависимые одной установкой, чтобы они типизировались против проверяемой
копии, а не против здорового дубликата из реестра. Сгенерированный
`consumer.ts` импортирует каждый объявленный типизированный вход каждого
пакета и должен пройти строгий `tsc --noEmit` с разрешением `nodenext`;
дополнительный импорт сгенерированного модуля доказывает, что каждый пакет
загружается под Node. npm не ставит опциональные peer-зависимости, поэтому
`@opencode/plugin` и `@types/node` ставятся явно по зафиксированным версиям —
по прецеденту registry-смоука. Кэш npm персистентен под `.build/`, поэтому
тёплый прогон занимает секунды; первый прогон оплачивает загрузку из реестра.

```shell
task package:consumer-smoke
```

Битый тарболл валит гейт, даже если та же версия остаётся здоровой в публичном
реестре — это класс «битый пакет уехал», который ловят только живые
потребители. Слой гейта зарегистрирован в `gate-registry.json`, поэтому CI-матрица
и скоуп-задание pre-push запускают его при изменении npm-поверхности.

## Детерминированное покрытие

Проверка секретов сканирует историю Git, текущие отслеживаемые и неигнорируемые
новые файлы. Игнорируемое состояние, например credentials локального Mattermost
и журналы публикаций, не является исходным кодом. Принудительно добавленный
игнорируемый файл становится отслеживаемым и тоже сканируется. Снимок сохраняет
содержимое симлинков без перехода по ним за пределы checkout.

Обычная проверка качества не обращается к модели или провайдеру и не требует
учётных данных; аудит зависимостей и контракты сайта документации входят в нее
и в матрицу CI:

```shell
task eval:check
task check
```

Зафиксированный набор сценариев содержит срабатывание и близкий отрицательный
пример на английском, а также срабатывание и близкий отрицательный пример на
русском для каждого активного навыка. Детерминированные проверки охватывают
регистрацию, конфигурацию, принадлежность файлов установщику, поведение архива и
`reconcile`, обнаружение агентов, недопустимые входные данные, выход за
разрешённые пути, некорректные результаты, неполные бюджеты и утечки секретов.

Для `spec-manage` у каждой области есть один основной владелец
детерминированной проверки. Hostless eval проверяет контракт корпуса, но не
наблюдает поведение модели:

| Область | Детерминированный владелец | Hostless-контракт eval | Поведение trusted-live |
| - | - | - | - |
| Язык, нормативные источники и расширения | `tests/test_spec_manage_contract.py` | двуязычный набор случаев и digests | выбор языка до записи, сохранение языка, конфликты, допустимые и недопустимые расширения |
| Validator snapshot и lifecycle | `tests/test_spec_validate.py` | только безопасность runner и invariants | не требуется |
| Требования, архитектура, ADR и locale parity | `tests/test_spec_manage_model.py` | не требуется | не требуется |
| Выбор режима, неоднозначность, near-miss и content states | `tests/test_spec_manage_evals.py` | двуязычный case protocol | outcome каждого случая и наблюдаемая граница без записи |
| Audit classification, severity, critic и aggregate | `tests/test_spec_manage_evals.py` | двуязычный case protocol | audit outcome каждого случая и наблюдаемая граница без записи |

Общим eval protocol и его отрицательными случаями владеет
`tests/test_evals.py`. Сценарии stage 20 для `spec-manage` проверяют только
декларации routing. Старые сценарии без `expected.case_outcomes` остаются
selection-only и не доказывают mode или audit outcomes. Offline-результат имеет
`observation_mode: hostless-contract`; только trusted-live использует
`observation_mode: trusted-live` и может подтвердить case outcomes.

Проверки совместимости запускаются для OpenCode, закреплённого в `mise.toml`
(см. `evals/contracts/opencode-compatibility.json`), в диапазоне
`>=2.0.0 <2.1.0` без учётных данных: smoke-проверки установленного tarball,
нативная оценка permissions на сервере V2 и контракт V2 HTTP и работы с базой
memomatic только для чтения.

## Реестр пропущенных дефектов

Аудит тестирования нашёл три класса дефектов, дошедших до `dev` мимо всех
гейтов. Каждый фикс попал в репозиторий вместе с тестами, но никто не доказывал,
что эти тесты краснеют на дофиксном поведении, а решения не моделировать
отдельные условия оставались неявными. Реестр делает и то и другое явным: по
каждому классу фиксируются симптом, причина пропуска гейтами, guard, который
теперь отвечает за класс, покрывающие тесты и статус доказательства.
Prove-by-removing означает, что в одноразовой копии checkout-а снимается
guard-часть фикса, сфокусированный тест краснеет с ожидаемой дофиксной
причиной, guard восстанавливается и тест снова зеленеет.

### Инстансы GitLab, игнорирующие запросы Range, фикс `b5cf464` — покрыт

Симптом: упавший job CI, чей трейс превышал стриминговый потолок 64 КиБ,
вызывал фатальную ошибку сбора и блокировал всю проверку на этапе prepared на
инстансах, отвечающих на запросы `Range` полным трейсом.

Почему гейты пропустили: расхождение среды. Офлайн-фикстуры и подменные ответы
`glab` моделировали только инстансы, соблюдающие `Range`; полный ответ
инстансов, игнорирующих `Range`, существует только на реальных установках, с
которыми офлайн-гейты не общаются.

Guard: `streamed_glab_trace` сохраняет последний ограниченный tail и помечает
поток как tail-dropped; `parse_glab_trace` и `glab_text` распространяют метку
как `complete=false`; `collect_pipeline_jobs` записывает усечённый tail как
свидетельство по job, пока защита метаданных, глубины и числа трейсов остаётся
фатальной.

Покрывающие тесты в `tests/test_application_workflows.py`:

- `test_gitlab_trace_streaming_enforces_limit_and_cleans_up_timeout` —
  слишком большой ответ даёт ограниченный фрагмент `complete=false` через
  `glab_text` вместо фатальной ошибки;
- `test_gitlab_trace_streaming_keeps_the_last_bounded_tail_bytes` —
  сохранённый фрагмент является последним ограниченным tail, а не головой;
- `test_gitlab_trace_completeness_requires_confirmed_full_range` —
  признак tail-dropped доходит до `complete=false`, а усечённый tail остаётся
  нефатальным свидетельством в `collect_pipeline_jobs`;
- `test_collect_pipeline_jobs_marks_trace_limit_overflow_truncated_without_fatal_error`
  — лимит числа трейсов помечает свидетельство усечённым без фатальной ошибки
  конвейера;
- `test_gitlab_trace_streaming_preserves_other_separator_in_body` и
  `test_gitlab_trace_streaming_accepts_exact_header_body_and_crlf_limits` —
  здоровые ответы не помечаются усечёнными.

Доказательство от 2026-10-05: снятие ветки сохранения tail краснило
`test_gitlab_trace_streaming_enforces_limit_and_cleans_up_timeout` и
`test_gitlab_trace_streaming_keeps_the_last_bounded_tail_bytes` с
`WorkflowError: GitLab job trace exceeds the response size limit`;
восстановление ветки снова делало оба теста зелёными. Восстановление
фатальной ошибки лимита трейсов краснило
`test_collect_pipeline_jobs_marks_trace_limit_overflow_truncated_without_fatal_error`
на проверке полноты конвейера; её повторное снятие снова делало тест
зелёным.

### Недоступный каталог моделей в мастере, фикс `184327d` — покрыт

Симптом: `install` прерывал настройку модели агента фатальной ошибкой
`catalog_unavailable`, когда каталог моделей OpenCode V2 было невозможно
прочитать, вместо приёма явно введённого provider/model.

Почему гейты пропустили: немоделируемая недоступность. TTY-тесты мастера
прогоняли только здоровый путь с рабочим каталогом под управлением живого
runtime OpenCode, а офлайн-стенда, имитирующего отказавший runtime, не было до
фикса, который ввёл подменный исполняемый файл `opencode`, завершающийся с
ненулевым кодом.

Guard: `modelSelection` ловит `catalog_unavailable`, предупреждает в stderr и
спрашивает явную модель и необязательный вариант вместо падения.

Покрывающие тесты в `packages/agentomatic/test/command-cli.test.mjs`:

- `TTY install falls back to an explicit model entry when the catalog is unavailable` —
  с отказавшим исполняемым файлом `opencode` мастер завершается успешно и
  применяет явно введённую модель;
- `TTY install stages a critic model from the catalog and applies it with one confirmation` —
  здоровый путь каталога сохраняет выбор из каталога.

Доказательство от 2026-10-05: проброс `catalog_unavailable` из
`modelSelection` прерывал мастер с `Error [catalog_unavailable]` до подсказки
явной модели и краснил fallback-тест; восстановление catch снова делало тест
зелёным.

### `prior_decisions` вне версии контекста, фикс `204714f` — закрыт в PORT-3

Симптом: значимое изменение согласованных решений не меняло версию контекста
вопроса, поэтому поздний ответ, собранный под отозванным исключением, мог
завершить проверку как готовую; документированное восстановление к тому же
удаляло свежие результаты других критиков, разделявших только устаревший ID
вопроса.

Почему гейты пропустили: недокументированный слой. Входные данные значимого
контекста перечислялись только в теле функции дайджеста; `prior_decisions`
отсутствовал и в этом списке, и в руководстве, README и спеке, поэтому ни
один контрактный тест не смотрел на смену решений.

Guard: `_shared_context_inputs` подаёт `prior_decisions` в оба дайджеста
`question_context_digest` и `question_context_version`; retirement фильтрует
каждый ответ и верификацию по собственной привязке (`is_current_result`), а не
только по ID вопроса, и переносит в историю только устаревшие записи.

Краснеющая проверка в
`apps/reviewmatic/tests/test_context_package.py::test_prior_decisions_change_both_package_and_question_context_bindings`
упадёт, если удалить `prior_decisions` из любого из двух дайджестов.
`apps/reviewmatic/tests/test_context_package_records.py` доказывает, что
изменение решения блокирует поздний ответ V1,
сохраняет авторство и исходные привязки в истории, оставляет свежий ответ V2 и
проверку другого критика и делает повторное восстановление идемпотентным.
`apps/reviewmatic/tests/test_local_review_scenarios.py` проверяет тот же запрет
устаревшего ответа и сохранение смешанных версий.
Проверка удалением: временно убрать `prior_decisions` из
`_shared_context_inputs`; прямой тест привязок должен упасть.

Статус: закрыто в PORT-3. Остаются покрытыми инварианты:

- `prior_decisions` участвует в `question_context_digest` и
  `question_context_version`;
- изменение согласованных решений устаревает поздние ответы, привязанные к
  прежней версии, поэтому они не могут завершить проверку как готовую;
- retirement сохраняет свежие результаты других критиков, переносит в историю
  только устаревшие записи с авторством и исходными привязками, хранит список
  ID вопросов как диагностику и остаётся идемпотентным при повторном
  восстановлении.

### Не моделируется офлайн

Два аспекта намеренно остаются вне офлайн-моделирования; риск несёт владелец репозитория:

- точное сетевое поведение версий GitLab, игнорирующих `Range` (разнообразие
  заголовков и чанков), моделируется только синтетически; живое поведение
  относится к ручному стенду интеграции GitLab, а не к гейту;
- реальный каталог OpenCode V2 и терминальный рендеринг в мастере
  моделируются подменным исполняемым файлом и форсированным TTY, поэтому
  разнообразие реальных runtime и терминалов остаётся вне гейтов.

Ослаблять покрывающие тесты, чтобы они проходили на немоделированном
поведении, запрещено; новое знание об этих аспектах попадает в репозиторий
как новые guard-ы со своим свидетельством prove-by-removing.

## Оценка на реальной модели и чистая рабочая копия

Оценка на реальной модели не входит в `task check`. Для неё нужно явно указать
режим `trusted-live`, среду, модель, тайм-аут, ограничения по токенам и стоимости,
а также путь для результатов. Модель и эталон по умолчанию не заданы,
недоверенная среда CI не получает учётные данные.

Сценарии с `expected.case_outcomes` требуют наблюдаемый результат для каждого
случая. Пропущенный, лишний, некорректный или malformed outcome проваливает eval.
Кейсы с контрактом `verify`, например пара `humanize` edit-contract, дополнительно
требуют, чтобы возвращённый `outcome` нёс полный отредактированный текст: harness
проверяет сам rewrite на побайтовую сохранность защищённых фрагментов, отсутствие
запрещённой пунктуации вне сохранённых точных цитат, сохранность заявленных
утверждений и отсутствие заявленных выдумок. Отсутствующий или дефектный rewrite
проваливает эти assertions, даже когда host сообщает об успехе.
Read-only boundary проверяется по diff проектного sandbox; сценарий `specs-only`
проваливается при изменении пути вне sandbox `specs/`. Live output является
приватным свидетельством конкретного запуска и не сохраняется в Git.

Общие копии среды выполнения существуют только в игнорируемых результатах сборки
и проверяются на идентичность. В чистой временной рабочей копии сборка и проверки
должны оставить `git status` неизменным. Тесты дистрибутива отдают полную структуру
Pages из локальной HTTP-фикстуры, устанавливают её через стабильную версию
`skills@latest`, удаляют фикстуру и затем запускают установленные скрипты. Перед
созданием GitHub Release среда CI выпуска дополнительно проверяет тег, версию,
ревизию исходников, каждый байт, опубликованный на Pages, точный tar-архив npm,
импорт пакета и CLI, подписи реестра, данные о происхождении по SLSA и контрольные суммы
разных каналов.

Тесты dev-публикации дополнительно проверяют детерминированную техническую версию
снимка, provenance источника `dev`, объединение корня Pages и `/dev`, а также
обязательный npm dist-tag `dev`. CI отклоняет pull request в `main` из веток вне
`dev`, `release/*` и `fix/*`, а также прямые пушы в `main` без merge-коммита;
branch protection репозитория остаётся внешней настройкой.
