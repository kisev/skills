# Обновление документации вместе с изменениями

[English](../../how-to/documentation-review.md)

## Выбор нужного шага

Согласованная спецификация определяет контракт; исходники и тесты показывают текущее
поведение. Нарушения действующей гарантии исправляйте в коде. Устаревшие описания
обновляйте по подтверждённым изменениям продукта. При конфликте нормативных источников
нужно решение владельца.

Для изменения поведения перед завершением задачи проверьте затронутые спецификации,
руководства, примеры, переводы и навигацию. Используйте `spec-manage` с `spec-update`
для канонической части и `docs-prepare` для пользовательских документов. Эти шаги
могут входить в одну разрешённую задачу. Сохраняйте предпосылки, ограничения, последствия
ошибок, совместимость, восстановление и объяснения; при переносе детали оставляйте ссылку.

Используйте `docs-review` для пользовательской документации и `spec-manage` с `spec-review`
для канонических спецификаций. Прежний режим проверки спецификации удалён
без алиаса. Область и глубина задаются отдельно от слова review:
полная проверка требует независимого критика; проверка изменений может использовать прежние результаты.

## Полезные связи с исходниками

Добавляйте короткий блок `review` в документы, когда он помогает выбрать материалы:

```yaml
---
review: {"components": ["example"], "sources": ["src/example/**", "tests/test_example.py"], "contracts": ["specs/requirements/interfaces/README.md"]}
---
```

Замените примеры существующими путями или glob относительно рабочей области. Укажите
общую реализацию и тесты, изменения которых влияют на документ, а не только
ближайший исходный файл. Метаданные должны совпадать в переводах. Для документа
без метаданных всё равно нужна оценка влияния; новые файлы без связей не исключаются.
Не поддерживайте хэши и даты проверки вручную: раннер записывает хэши исходников.

```shell
task docs:check
task locale:check
```

Эти команды проверяют структуру, объявленные зависимости, каталоги, ссылки и
переводы. Они не доказывают смысловую корректность или полноту покрытия.

## Повторное использование проверки

Установленные скиллы `docs-review` и `spec-manage` содержат
`scripts/documentation_review.py`. Их workflow вызывают `prepare` с рабочей областью,
границами и идентификатором сессии, читают предыдущий результат и сохраняют
новый отчёт. Отдельная установка или плагин OpenCode не требуются.

- `full`: первая база или явно запрошенная новая полная проверка; один независимый критик.
- `incremental`: изменённые исходники, затронутые документы, прежние замечания и решения пользователя.
- `unchanged`: сохранённые результаты и ограничения; повторный вызов сам по себе не запускает полный анализ.

Непубличные записи находятся в `${XDG_STATE_HOME:-$HOME/.local/state}/agent-skills/documentation-review/`,
раздельно по рабочим областям и границам. Они сохраняют хэши файлов, замечания, решения,
проверенные и непроверенные области и фактические результаты проверок. Байтов исходников
в них нет; нельзя копировать туда учётные данные или приватные расшифровки. Изменившийся
снимок блокирует сохранение результата: повторите подготовку и проверьте затронутые данные.

Пользователь может удалить непубличное состояние проверки; следующий вызов создаст полную
базу. Сохранённый результат не разрешает публикацию и не доказывает отсутствие всех
возможных дефектов. Принятые риски сохраняются до изменения фактов или решения
пользователя; неизменившийся хэш не закрывает непроверенную область.
