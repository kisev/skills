# Настройка и использование Memomatic

[English](../../how-to/memomatic.md)

## Установка и подключение

Нужны Node.js 22.13+ и npm. Для CLI, доступного за пределами npm-проекта:

```shell
# Registry version
npm view --prefer-online @kisev/memomatic@latest version

# Install
npm install --global @kisev/memomatic

# Installed package and active CLI
npm list --global @kisev/memomatic --depth=0
memomatic --version
```

Теги могут сдвинуться между просмотром и установкой. `npm list` проверяет пакет,
`--version` - CLI из PATH. Для установки в проект:

```shell
# Registry version
npm view --prefer-online @kisev/memomatic@latest version

# Install in this npm project
npm install @kisev/memomatic

# Installed dependency and local CLI (no npx download)
npm list @kisev/memomatic --depth=0
./node_modules/.bin/memomatic --version
```

Вызывайте CLI проекта через `npx memomatic`. Пример systemd ниже рассчитан на
глобальный бинарник. Сам npx не устанавливает CLI глобально.

Подключите `memomatic mcp-serve` как локальный MCP-сервер stdio в каждом хосте.
В JSON-конфигурации OpenCode, Kilo и MiMo используется такой фрагмент:

```json
{
  "mcp": {
    "memomatic": {
      "type": "local",
      "command": ["memomatic", "mcp-serve"],
      "enabled": true
    }
  }
}
```

Объедините его с существующими MCP-записями. Если сервис не находит бинарник,
установленный через менеджер версий, задайте абсолютные пути исполняемых файлов.
Перезапустите хост и проверьте наличие `memory_write`, `memory_search`, `memory_get`
и `memory_forget` у MCP-сервера (хост может добавлять префикс к именам инструментов).
Модель сама решает, когда искать; если поиск обязателен, попросите об этом явно.
Автоматической подстановки памяти нет.

Memomatic и agentomatic устанавливаются отдельно; agentomatic не устанавливает
memomatic и не зависит от него.
`@dev` выбирает последнюю успешную публикацию из `dev` для всех workspace-пакетов:
`@kisev/agentomatic`, `@kisev/memomatic`, `@kisev/taskmatic` и `@kisev/safe-fs`.
`@latest` - канал стабильных релизов; до первого стабильного релиза пакета его
первоначальный тег в реестре может ещё указывать на prerelease. Для dev-установок
явно указывайте `@dev`:

```shell
# Registry versions
npm view --prefer-online @kisev/memomatic@dev version
npm view --prefer-online @kisev/agentomatic@dev version

# Install and confirm the OpenCode setup
npm install --global @kisev/memomatic@dev
npx --yes @kisev/agentomatic@dev install --global

# Installed packages and active memory CLI
npm list --global @kisev/memomatic --depth=0
npm list --prefix "$HOME/.config/opencode" @kisev/agentomatic --depth=0
memomatic --version
```

Обновление agentomatic не обновляет CLI и MCP-сервер memomatic.

## Переход с плагина OpenCode

Повторно запустите [установщик agentomatic](opencode-integration.md) с прежним
выбором компонентов, кроме `memomatic`: такого варианта плагина больше нет.
Проверьте предпросмотр: неизменённый `plugins/memomatic.js`, принадлежащий
установщику по манифесту, архивируется и удаляется. Изменённая обёртка вызывает
конфликт; сохраните свои правки и разрешите его перед повторным запуском.
Если вы вручную прописали импорт `@kisev/agentomatic/plugins/memomatic`, удалите
эту запись самостоятельно. Затем подключите MCP-сервер по примеру выше и
перезапустите OpenCode. Обновление только npm-зависимости не удаляет старую обёртку.

Файлы памяти, inbox, эмбеддинги, правила и существующее расписание проходов
сохраняются.
Прежний маппинг `projects` в настройках игнорируется; аннотации проекта и
триггеров остаются в существующих записях, но больше не вызывают автоматический recall.

## Первая запись и поиск

Попросите агента вызвать `memory_write` с `text: "Use a separate preview before publishing."`
и `source: "user"`. Результат указывает на файл в очереди inbox, а не на проиндексированный факт.
Затем выполните:

```shell
memomatic process
memomatic search "preview publishing"
```

Вызовите `memory_get` с полученными файлом и строкой для чтения полной записи.
Результаты поиска указывают источник и личную или командную видимость. Личную запись
нельзя копировать в общие артефакты. `memory_forget` удаляет одну явно выбранную
строку; обычная модельная консолидация не разрешает удалять кураторскую память.

## Настройка Sessions и Dream

Sessions и Dream — независимые проходы. `memomatic sessions` извлекает
эпизодическую память из транскриптов сессий OpenCode; `memomatic dream`
консолидирует: inbox, продвижение прошедших пороги использования эпизодических
записей в `MEMORY.md`, ограниченная перезапись и архивирование. Dream сам не
читает историю OpenCode.

Перед извлечением знаний из сессий установите OpenCode, настройте провайдера
и выберите доступную модель через `opencode models`. Создайте
`${XDG_CONFIG_HOME:-$HOME/.config}/memomatic/settings.json` с выбранным
идентификатором `provider/model`:

```json
{"sessions": {"model": "provider/model"}}
```

Старое значение `{"dream": {"model": "provider/model"}}` продолжает работать
для Sessions, пока секция `sessions` не переопределит его.

```shell
memomatic sessions --dry-run
memomatic sessions
memomatic dream
```

Предпросмотр сохраняет файлы памяти, постоянный индекс и отметку обработанных
сессий; настроенные вызовы модели и эмбеддингов могут выполняться. Без модели
`sessions` пропускается без продвижения отметки; `dream` по-прежнему обрабатывает
inbox и архивирует по правилам, но не вызывает модель консолидации.
Для прохода inbox без модели используйте `process`. Невалидный ответ консолидации
включает ограниченное добавление записей с сохранением существующей кураторской памяти.

Команда sessions читает сессии OpenCode из базы V2, извлекая только
пользовательский текст и ответы ассистента. База до V2 не разбирается:
запустите OpenCode V2 один раз, чтобы он перенёс историю, и повторите проход.
MCP-подключения в других хостах используют общие явные записи памяти, но не
импортируют историю сессий этих хостов. Вызовы модели используют один отдельный
сервер OpenCode V2 на проход с запрещёнными инструментами либо явно указанный
существующий сервер. Перед включением таймера
сопоставьте `sessionsIngested` с доступными необработанными сессиями: проход с нулём
сессий не проверяет доступ к модели.

## Наблюдение, ограничения и продолжение Dream

```shell
memomatic sessions --plan --json
memomatic sessions --max-duration 15m --timeout 3m --log-format json
memomatic sessions --max-sessions 2 --progress never
memomatic dream --plan --json
memomatic status
memomatic sessions --help
```

`sessions --plan` только читает снимок сессий и контрольные точки: без вызова
модели, эмбеддингов и постоянных записей. `dream --plan` так же считает ожидающие
файлы inbox и кандидатов на продвижение. `status` показывает очередь без модели:
ожидающие файлы inbox, бэклог сессий (или `null`, когда базы OpenCode нет),
кандидатов на продвижение и время последнего прохода dream/sessions. В отличие
от `--plan`, `--dry-run` может расходовать ресурсы модели и эмбеддингов. Обычный
Sessions обрабатывает всю доступную на старте очередь; последующие сообщения
попадут в следующий запуск. Прежнего ограничения в 20 сессий по умолчанию нет.
При первом обновлении старый курсор времени создания не позволяет определить
обработанные редакции сообщений, поэтому история перепроверяется один раз.
Накопленная память сохраняется. Сначала посмотрите `--plan`; ограничения
позволяют распределить большую миграцию на несколько запусков. Это повторное
извлечение, а не удаление или замена корпуса памяти.

| Параметр CLI | Env | Настройка `sessions` / значение по умолчанию |
| - | - | - |
| `--model` | `MEMOMATIC_MODEL` | `model`: настроенный provider/model |
| `--variant` | `MEMOMATIC_VARIANT` | `variant`: значение провайдера |
| `--timeout` | `MEMOMATIC_TIMEOUT` | `timeoutMs`: 180000 |
| `--max-duration` | `MEMOMATIC_MAX_DURATION` | `maxDurationMs`: 0 (без ограничения) |
| `--max-sessions` | `MEMOMATIC_MAX_SESSIONS` | `maxSessions`: 0 (все) |
| `--chunk-chars` | `MEMOMATIC_CHUNK_CHARS` | `maxChars`: 24000 |
| `--retries` | `MEMOMATIC_RETRIES` | `retries`: 1 дополнительная попытка |
| `--idle` | `MEMOMATIC_IDLE` | `idleMs`: 600000 |
| `--opencode-url` | `MEMOMATIC_OPENCODE_URL` | `opencodeUrl`: отдельный сервер на проход |
| `--database` | `MEMOMATIC_DATABASE` | XDG-база OpenCode |

Dream сохраняет параметры `--model`, `--variant`, `--timeout`, `--max-duration`
и `--retries` для модели консолидации; соответствующие настройки живут в секции
`dream` (`model` также служит запасным значением для sessions). Прежние параметры
извлечения из секции `dream` автоматически мигрируют в `sessions` при первой
загрузке.

Длительности в CLI принимают `ms`, `s`, `m`, `h`; число без суффикса означает
миллисекунды. В файле настроек длительности числовые, в миллисекундах. Общие
параметры логирования, JSON и цвета описаны в [справочнике CLI](../reference/cli.md).

SQL отбирает текстовые части до загрузки в приложение. Неизменённые редакции
современных сессий пропускаются без разбора тел; изменённые сообщения проверяются
по отпечаткам и делятся на фрагменты без обрезания финального результата.
Убираются только соседние точные повторы сообщений; эвристического отбора
«важных сообщений» нет. Фрагмент получает ограниченное перекрытие предыдущего
контекста. Модель всё ещё может не восстановить далёкую ссылку; ей запрещено
выдумывать смысл неразрешимых ссылок.

Завершённые ответы извлечения сохраняются приватно в `history/ingestion/` с
идентификаторами исходных сессий и сообщений, без полных транскриптов. Фрагмент
применяется идемпотентно до продвижения контрольной точки. Ctrl-C, таймаут или
поздняя ошибка сохраняют уже завершённую работу. Повторите команду для продолжения;
не удаляйте run lock, пока жив его владелец. Блокировка больше не истекает просто
из-за превышения 30 минут. После прерывания индекс может отставать от сохранённого
Markdown; продолжите прерванную команду или выполните `memomatic index`.

Этапы, счётчики, прошедшее время, повторы и сообщения ожидания идут в stderr.
Итоговый JSON содержит число вызовов, отправленные символы и реальные токены/кэш,
если OpenCode их сообщает; отсутствие usage отмечается явно, а не заменяется
оценкой под видом точных данных. При лимите сессий отдельно показано число
непросмотренных сессий и остаток фрагментов выбранной порции.

Исполнитель использует настройки провайдеров и авторизацию OpenCode, отключает
внешние плагины/скиллы у собственного сервера и запрещает инструменты в сессиях
извлечения. Его loopback-сервер защищён временным паролем и завершается вместе с
проходом или отменой. `--opencode-url` выбирает ваш существующий сервер; при
необходимости используются `OPENCODE_SERVER_USERNAME`/`OPENCODE_SERVER_PASSWORD`.
Такой сервер memomatic не останавливает. Учётные данные не передаются аргументами
CLI и не попадают в поля логов.

`memomatic index` теперь переиспользует векторы при неизменных тексте и модели.
`memomatic index --force` принудительно пересоздаёт все векторы, в том числе после
смены весов/размерности за прежним именем модели. `memomatic status` только читает
состояние и больше не перестраивает индекс.

## Настройка локальных эмбеддингов

Эмбеддинги необязательны и по умолчанию отключены. Без них память использует
текстовый поиск FTS5. Для векторного поиска через Ollama запустите Ollama и
установите embedding-модель, например `qwen3-embedding:4b`, затем добавьте в
`settings.json` рядом с `sessions` и `dream` этот блок:

```json
{
  "embedding": {
    "url": "http://127.0.0.1:11434/v1/embeddings",
    "model": "qwen3-embedding:4b"
  }
}
```

URL должен указывать на OpenAI-совместимый endpoint эмбеддингов, а не на
`/api/embed` Ollama. Полный URL, модель, авторизация, таймаут и ограничения
запросов настраиваются для каждого сервиса в `settings.json`; конкретный сервер
в код не зашит. Подойдёт любое OpenAI-совместимое развёртывание, включая vLLM:

```json
{
  "embedding": {
    "url": "http://127.0.0.1:8080/v1/embeddings",
    "model": "embedding",
    "queryPrefix": "query: ",
    "documentPrefix": "passage: ",
    "bearerEnv": "EMBEDDING_TOKEN",
    "timeoutMs": 120000,
    "maxBatchTexts": 32,
    "maxTextChars": 8000
  }
}
```

`queryPrefix` и `documentPrefix` форматируют запросы и документы независимо;
по умолчанию обе стороны — обычный текст, а инструкция Qwen3 `Instruct`/`Query`
всё ещё добавляется к запросам автоматически для моделей Qwen3, пока
`embedding.queryInstruction` её не переопределит (явное пустое значение
отключает обёртку). `bearerEnv` задаёт имя переменной окружения с Bearer-токеном;
он отправляется как `Authorization: Bearer ...` и никогда не попадает в логи;
токен с управляющими символами отклоняется до любого запроса, поэтому его
значение не попадает и в сообщения об ошибках. `timeoutMs` по умолчанию 30000;
увеличьте его для сервера, который загружает
модель при первом запросе. `maxBatchTexts` ограничивает число входов в одном
запросе, `maxTextChars` — длину одного форматированного фрагмента; длинные
входы сначала разбиваются по границам абзацев, строк или пробелов, затем каждый
фрагмент форматируется, эмбеддинги считаются по фрагментам и
усредняются в один вектор записи, поэтому длинные записи попадают в выдачу
один раз. 8000 символов — консервативный прокси типового бюджета 4096 токенов
(примерно два символа на токен для плотных письменностей), а не точный подсчёт
токенов.

Memomatic отправляет `encoding_format: "float"` и читает векторы из
`data[i].embedding`, восстанавливая порядок запроса по `data[i].index`. После
смены модели или форматирования документов выполните `memomatic index`, затем
проверьте `memomatic search`. Endpoint должен быть доступен при индексации и
поиске: сбой запроса эмбеддингов возвращает ошибку, а не включает незаметно
текстовый поиск.

## Необязательный реранкинг

Реранкер переупорядочивает более широкий набор кандидатов cross-encoder-моделью.
По умолчанию он отключён и работает как с эмбеддингами, так и без них:

```json
{
  "reranker": {
    "url": "http://127.0.0.1:8080/rerank",
    "model": "reranker",
    "bearerEnv": "RERANKER_TOKEN",
    "timeoutMs": 120000,
    "candidates": 64,
    "minScore": 0,
    "maxDocuments": 64,
    "maxChars": 8000
  }
}
```

Endpoint получает `POST` с телом `{model, query, documents, top_n}` и должен
вернуть `{results: [{index, relevance_score}]}` — этот контракт обслуживают
`/rerank` в vLLM и совместимые с Jina/Cohere реранкеры. Документы уходят обычным
текстом записей без embedding-префиксов. При включённом реранкере лексический и
векторный поиск сначала собирают до `candidates` кандидатов каждый, пропуская
строгие пороги релевантности; фильтр проекта применяется до отправки. Оценка
реранкера становится итоговой релевантностью и порядком — точное совпадение
ключевых слов больше не выигрывает безусловно, а `reranker.minScore` (по
умолчанию 0) отбрасывает слабые результаты. Оценки — сигналы ранжирования, а не
универсальные вероятности; их шкала зависит от модели, поэтому калибруйте
`minScore` на собственных примерах релевантных и нерелевантных записей. Длинные
документы разбиваются так, чтобы запрос, один фрагмент документа и шаблон
сервера умещались в `maxChars`; запрос, которому не хватает места хотя бы на
один фрагмент, завершается ошибкой до отправки. Поскольку `top_n` равен числу
отправленных документов, пустой или укороченный ответ — это ошибка, а не пустой
результат. Оценки фрагментов объединяются по максимуму, и
запись попадает в выдачу не более одного раза. Ошибки, неполные или некорректные
ответы и таймауты реранкера завершают поиск явной ошибкой вместо переключения на
другой режим. Смена настроек реранкера никогда не требует переиндексации — только
смена embedding-модели или обработки документов.

## Качество поиска и диагностика

```shell
memomatic index
memomatic search "routing decisions" --explain
memomatic search "deployment" --project atlas --explain
```

После обновления индекса без метаданных модели один раз выполните `memomatic index`.
Команда пересобирает производные поисковые данные и эмбеддинги, а не Markdown-знания
или историю сессий. Отпечаток индекса покрывает endpoint, модель, префикс
документов, бюджет фрагментов и версию обработки документов; изменение любого
из них требует повторной индексации — сюда входит и апгрейд memomatic, когда
меняется обработка документов (как при переносе разбивки до форматирования).
Векторы
разных моделей несовместимы даже при одинаковой размерности. При сбое
эмбеддингов прежний индекс сохраняется, а команда сообщает об ошибке.

Для Qwen3-Embedding поиск автоматически добавляет инструкцию `Instruct`/`Query`
к запросам; документы остаются обычным текстом, кроме префикса. Для других
моделей запросы не изменяются, пока не задан `embedding.queryInstruction`.
Явная пустая инструкция отключает обёртку. Длинные входы разбиваются до
форматирования, поэтому каждый фрагмент документа несёт
`embedding.documentPrefix`, а каждый фрагмент запроса — префикс запроса и
инструкцию, и умещается в `embedding.maxTextChars`; обёртка, не оставляющая
места тексту, даёт явную ошибку. Смена инструкции или префикса запроса не
требует пересчёта векторов документов; смена `embedding.documentPrefix` или
`maxTextChars` — требует.

Полные совпадения токенов идут первыми. Покрытие слов запроса и векторное сходство
проверяются до поправок на важность и возраст; лексическое совпадение не снижает
релевантность. Чисто смысловой результат должен достигать `search.minSemanticScore`
(по умолчанию `0.45`). Общий `search.minScore` остаётся `0.35`; это настраиваемые
пороги, а не вероятности. Значения проверены на небольшой локальной выборке Qwen3,
а не на универсальном бенчмарке. Другая модель может давать иные оценки; высокий
порог способен отсечь слабое, но полезное смысловое совпадение.

При включённом реранкере прежние строгие пороги кандидатов не отбирают — набор
собирается до любых порогов релевантности, а итоговый отсев задаёт
`reranker.minScore`; `--explain` сообщает
`reason: "rerank"` с оценкой реранкера, числом кандидатов и порогом. Без
реранкера `--explain` показывает совпавшие токены, покрытие запроса, косинусное
сходство, релевантность, возраст, важность и причину включения. MCP принимает
`explain: true` и `project` у `memory_search`. Без подходящих записей CLI печатает
`No relevant memory found.`, а MCP возвращает `[]`. Ошибка эмбеддингов или
реранкера не маскируется под успешный поиск с пустым результатом.

Фильтр проекта включает записи именно этого проекта и пользовательский слой памяти;
старым записям без аннотаций область не назначается автоматически. Человеческие
инструкции остаются в файлах правил репозитория и хоста. Найденный опыт и предпочтения
служат сведениями, а не разрешением переопределить правила. Это соответствует
[принципам Z.ai](https://docs.z.ai/devpack/resources/memory-mechanism): разделение
инструкций и накопленного опыта, поиск с учётом области и проверяемые обновления.
Доступ агента остаётся явным MCP-вызовом.

## Хранение, очистка и восстановление

Корпус находится в `${XDG_STATE_HOME:-$HOME/.local/state}/memomatic/`:
`MEMORY.md`, `USER.md`, ежедневные файлы в `memory/`, `DREAMS.md`, `inbox/`,
`history/` и `archive/`. Правила находятся в
`${XDG_CONFIG_HOME:-$HOME/.config}/memomatic/MEMORY_RULES.md`.

```markdown
- never-save: credentials
- auto-clean: older-than=90d scope=episodic source=handoff
- auto-clean: older-than=180d scope=episodic unused-after=30d
```

Очистка архивирует только подходящие старые незакреплённые записи и сохраняет
остальные записи того же файла. Необязательный суффикс `unused-after=Nd` добавляет
распад с учётом использования: эпизодические записи старше `Nd` дней без ни одного
полезного recalled-обращения архивируются раньше, а используемые живут до полного
срока `older-than` или продвижения. Без суффикса распад неактивен. Отклонённые
файлы inbox остаются в `inbox/rejected/`.
Проверяйте их после отказа. Чтобы отменить нежелательное изменение, найдите
предыдущее содержимое по хэшу в `history/` или выбранные записи в `archive/`,
восстановите нужный текст корпуса и выполните `memomatic index`. Эти данные
должны оставаться приватными и вне Git.

## Запуск по расписанию

Юниты принадлежат `@kisev/memomatic`, а не agentomatic. Найдите их через
`npm root --global`, затем скопируйте четыре юнита из
`<npm-root>/@kisev/memomatic/assets/systemd/` в `~/.config/systemd/user/`.
Убедитесь, что пользовательский сервис находит `memomatic` и `opencode`; задайте
абсолютные пути или явный PATH сервиса, если бинарники предоставляет менеджер версий оболочки.

```shell
systemctl --user daemon-reload
systemctl --user enable --now memomatic-sessions.timer memomatic-dream.timer
systemctl --user status memomatic-sessions.timer memomatic-dream.timer
journalctl --user -u memomatic-sessions.service
journalctl --user -u memomatic-dream.service
```

Sessions запускаются рано (02:00 с разбросом), Dream позже (04:30 с разбросом),
поэтому извлечение обычно завершается до консолидации. Оба прохода используют
один run lock: если необычно долгий sessions пересечётся с Dream, этот запуск
Dream завершится ошибкой `another memomatic run is active`, и следующий
запланированный проход подхватит работу. Включайте таймеры после успешных
ручных проходов. Команда
`systemctl --user disable --now memomatic-sessions.timer memomatic-dream.timer`
отключает расписание и сохраняет память.
