# Вклад в Agent Skills

[English](CONTRIBUTING.md)

## Область изменений

Каждый каталог в `skills/` содержит редактируемое описание, а не результат
установки. Сборка должна превращать каждое описание в переносимый и
самодостаточный навык без зависимости от копии репозитория, домашнего каталога
пользователя, конкретного поставщика, учетных данных или конфигурации отдельной
команды. Размещение по хостам, диалекты и форматы команд находятся только
в реестре адаптеров `skillmate` внутри `apps/skillmate/`.

Согласуйте существенное изменение поведения, совместимости или границ
безопасности до реализации. Новому исполняемому модулю нужен наблюдаемый
контракт: JSON в `stdout`, диагностика в `stderr`, определенные коды возврата,
`--help` и `--capabilities`. Классифицируйте запись по
[общему контракту взаимодействия](shared/references/interaction-contract.md):
ограниченные изменения файлов проекта выполняются напрямую; внешняя публикация,
пользовательская конфигурация, разрушительная очистка, изменения истории, релизы
и операции жизненного цикла пакета требуют точного preview и подтверждения.

## Локальная проверка

Установите закрепленные среды выполнения и отдельные инструменты из корня
репозитория:

```shell
mise install
task install
task --list
```

`taskfile.yml` является полным графом задач репозитория и CI. Lefthook
запускает быструю pre-commit-проверку staged-файлов (закрепленные lint-инструменты
напрямую плюс прицельные проверки типов и тестов); pre-push и GitHub Actions
вызывают публичные задачи. Перед отправкой любого изменения выполните единую
проверку качества:

```shell
task check
```

Имена задач следуют таксономии `объект:действие` с фиксированным словарём
действий (`lint`, `format`, `typecheck`, `test`, `build`, `check`, `install`,
`audit`, `bench`, `scan`, `smoke`, `render`); задокументированное исключение —
зонтичные группы (`lint`, `format`, `typecheck`, `test`, `check`,
`check:core`, `generate`). Основные публичные задачи распределяют проверки
следующим образом:

| Задача | Назначение |
| - | - |
| `install` | Установить закрепленные инструменты, зависимости и хуки Git. |
| `tools` | Показать активный набор закрепленных инструментов. |
| `format` | Отформатировать поддерживаемые исходные файлы. |
| `lint`, `typecheck`, `test` | Проверить исходники, форматирование, типы и тесты. |
| `generate`, `generate:check` | Собрать игнорируемые артефакты или проверить их воспроизводимость. |
| `skills:check` | Выполнить проверки Agnix и `agentskills`. |
| `package:check` | Проверить полный жизненный цикл пакета OpenCode. |
| `eval:check` | Проверить данные оценок и запустить автономный набор без среды агента. |
| `dependency:audit` | Проверить зафиксированные графы зависимостей Python и npm. |
| `secrets:scan` | Найти секреты в истории Git и рабочей копии с помощью gitleaks. |
| `gates:check` | Сообщить об ошибке при расхождении отрисованной копии gate с `gate-registry.json`. |
| `check:core` | Запустить постоянное ядро, общее для каждого push-gate. |
| `check` | Запустить полный набор локальных проверок и проверок CI. |
| `pre-push` | Запустить полный неселективный локальный gate для ручной и release-проверки. |

`task format` может изменить отслеживаемые файлы, а `task generate` создает
только игнорируемые артефакты. Редактируемые точки входа переносимых навыков
называются `SKILL.source.md`; `scripts/build_skills.py` создает `SKILL.md` и
добавляет файлы, объявленные в `shared/manifest.json`, только в `.build/skills`.

`package:check` устанавливает зафиксированные npm-зависимости, один раз собирает
workspace, запускает тесты Node.js и проверяет состав npm-пакетов по спискам
разрешенных файлов. За lint и проверку типов отвечают корневые задачи, поэтому
жизненный цикл пакета их не повторяет.

`dependency:audit` проверяет зафиксированные графы зависимостей Python и npm
и входит в `check:core`, поэтому полный локальный gate и матрица CI выполняют
ее; для работы она обращается по сети к внешним сервисам с данными об
уязвимостях.

`gate-registry.json` — единственный источник состава gate: одна запись на слой
сопоставляет входные пути с задачей gate. `scripts/generate_gates.py`
отрисовывает из реестра блоки `matrix.include` в CI и списки glob в pre-push
Lefthook; политика веток, скелеты задач, агрегация и вызовы задач остаются
рукописными. `task gates:check` выполняется в `check:core` и в CI и сообщает
об ошибке, когда отрисованная копия, граф задач или скелет расходится с
реестром; после правки реестра выполните `task gates:render`.

## Диагностика

- Если исполняемый файл недоступен, выполните `mise install` и проверьте версии с
  помощью `mise current`.
- Если `uv run --locked` сообщает о расхождении, осознанно обновите закрепленную
  версию в `pyproject.toml`, затем выполните `uv lock`; не обновляйте зависимости
  неявно. Все закрепления используют актуальный шаблон `== major.minor.*`, поэтому
  `uv lock --upgrade` подхватывает патч-релизы, а минорные и мажорные обновления
  остаются осознанными.
- Если `generate:check` сообщает о расхождении, исправьте исходный файл и
  выполните `task generate`; не редактируйте результат сборки напрямую.
- Ошибки Agnix блокируют проверку. Существующие предупреждения выводятся и
  записываются в `.agnix-warnings.json`; новое предупреждение также блокирует
  проверку, пока причина не устранена или эталонный список не обновлен осознанно.
- Чтобы воспроизвести ошибку пакета, запустите `task package:check` из корня
  репозитория. Так сохранятся версии и порядок действий из CI.

## Качество и проверка изменений

- Сохраняйте frontmatter и ограничения формата agentskills.io для каждого
  `SKILL.source.md`; собранный файл называется `SKILL.md`, а метаданные исходного
  и собранного навыка не содержат версию.
- Добавляйте точечные тесты для публичных контрактов или при существенном риске
  регрессии, а не для деталей реализации.
- Не включайте в изменения учетные данные, токены, внутренние адреса, локальные
  пути, кеши, результаты оценок на реальных моделях или артефакты сборки.
- Запускайте оценки на реальных моделях только явно и с точными значениями
  `--host`, `--model`, `--timeout`, `--max-tokens`, `--max-cost` и `--output`. Не
  добавляйте в Git модели по умолчанию или результаты таких запусков; обычный CI
  выполняет только автономный набор проверок.
- В запросе на включение изменений указывайте цель, влияние на безопасность,
  выполненные и осознанно пропущенные проверки.
- Используйте английский язык для кода, комментариев и сообщений коммитов;
  пользовательская документация следует языку существующего раздела. Сохраняйте
  машинные токены без изменений.

## Хуки Git

Установите хуки после подготовки среды:

```shell
lefthook install
```

`pre-commit` проверяет только измененные файлы. Быстрые проверки lint и
secrets выполняются напрямую для staged-файлов закрепленными инструментами
Mise, strict mypy покрывает измененные исходники Python, проектный `tsc` —
измененный TypeScript, затронутые pytest-файлы запускаются в раннере своего
проекта, а каждый затронутый workspace-пакет пересобирается без очистки `dist`
и проходит свой npm-сьют тестов. Удаленные пути исключаются; полные сьюты,
сборки с очисткой, генерация и release-проверки остаются за pre-push и CI.

`pre-push` выбирает задачи по дельте пуша: дельта вычисляется относительно
апстрима ветки, а когда его нет, откатывается ко всем отслеживаемым файлам,
поэтому первые пуши проходят полный gate. Задачи исполняются параллельно,
зеркаля дублируемую ими CI-матрицу, поэтому локальный gate укладывается
с запасом в окно простоя SSH-транспорта. Постоянная задача запускает
`task check:core`, куда входят слои документации, сайта документации и аудита
зависимостей; `task python:test` и `task package:check` выполняются, только
если дельта затрагивает входы их стека, а каждый селективный список glob
несет мета-триггеры, поэтому правки инструментов запускают все слои. CI
повторяет полный gate на каждый пуш, поэтому селективность не сокращает
проверку, а `task pre-push` остается неселективным gate для ручной
диагностики и релизов. Хуки не исправляют файлы и не выполняют `git add`.

## Выпуски

Переносимые навыки не имеют собственных версий. Выпуск определяется метаданными
дистрибутива GitHub Pages и контрольной суммой каждого адресуемого по содержимому
архива. Дистрибутив GitHub Pages, манифест переносимой версии, тег и GitHub
Release должны относиться к одному коммиту. Не изменяйте опубликованную версию;
вместо этого публикуйте новую патч-версию.

Используйте `dev` как ствол разработки: по умолчанию отправляйте в него прямые
коммиты, а feature- и fix-ветки с pull request в `dev` — только когда ветка
действительно помогает. `main` изменяется исключительно pull request с
merge-коммитом и отражает последнюю стабильную фича-линию. Выбранную
сопровождающим stable-версию и оба changelog подготовьте в `dev`; если точка
релиза не совпадает с головой `dev`, отрежьте релизную ветку от выбранного
коммита и готовьте в ней. Само объединение релиз не публикует.

Фича-релиз `X.Y.0` выходит через pull request в `main`, тег ставится на
получившийся merge-коммит. Патч последней фича-линии `X.Y.z` выходит так же —
из `dev` или ветки `fix/*`. Когда выходит следующий фича-релиз, отрежьте
`release/vX.Y` от последнего тега предыдущей линии и обновите в ней релизную
автоматизацию: пуш тега запускает `.github/workflows/publish.yml` от
тегированного коммита, и устаревший workflow опубликовал бы патч старой линии
не на том канале. Патчи старых линий идут через pull request из `fix/*` в
`release/vX.Y` с тегом на merge-коммите.

Запускайте проектный навык `project-release` для управляемого выпуска. Он отдельно
запрашивает подтверждение перед отправкой релизной ветки, объединением в `main`,
созданием аннотированного тега `vX.Y.Z` и отправкой этого тега. Тег должен
указывать на получившийся merge-коммит.

Тег запускает `.github/workflows/publish.yml`. Он повторно проверяет
опубликованные тег и ревизию, определяет канал публикации по тегированному
коммиту и собирает манифест происхождения. Для коммита из `main` он
разворачивает stable-канал GitHub Pages; для коммита из `release/vX.Y` он
пропускает Pages; в обоих случаях затем создается GitHub Release с точной
секцией changelog. Пакет `skillmate` на PyPI публикуется через доверенную
публикацию (OIDC) с тегов `main`.

Для каждого push в `dev` CI выполняет полный gate на запушенной ревизии, а
publication workflow дожидается его терминального заключения `success` для той
же ревизии и только затем пересобирает точные артефакты и заменяет канал Pages
`/dev`. Если этот run завершился ошибкой, был отменен более новым пушем или
отсутствует, публикация прекращается. Dev-снимки не выбирают stable SemVer и не
создают GitHub Release.
