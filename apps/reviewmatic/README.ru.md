# reviewmatic

[English version](README.md)

`@kisev/reviewmatic` — исполняемый рантайм скилла `code-review`: полная цепочка
ревью (сбор доказательств GitLab, машина состояний ревью, иммутабельные планы,
ручная публикация) плюс интерактивный терминальный разбор готового плана
ревью.

## Установка

```bash
# Registry version
npm view --prefer-online @kisev/reviewmatic@latest version

# Install
npm install --global @kisev/reviewmatic

# Installed package and active CLI
npm list --global @kisev/reviewmatic --depth=0
reviewmatic --version
```

Тег может сдвинуться между просмотром и установкой; последние команды показывают
установленный пакет и CLI из PATH. Для `@dev` измените и команду просмотра,
и команду установки.

Нужны Node.js 22.13+ и аутентифицированный для вашего GitLab CLI `glab`.
Для dev-дистрибутива скилла установите `@kisev/reviewmatic@dev`, а не стабильный
npm-канал. Если в OpenCode подключён core plugin agentomatic, обновите и этот
пакет, затем перезапустите OpenCode: обновление CLI само по себе не перезагружает
hooks маршрутизации сабагентов. Дополнительные профили агентов всё ещё необязательны.
Состояние ревью хранится в `$XDG_STATE_HOME/agent-skills/gitlab/<target-key>/` - там же,
куда пишут команды ревью.

## Цепочка ревью

Агент заполняет один редактируемый черновик, не перенося привязки между файлами
decision и content:

```bash
reviewmatic start-review --url <mr-url> --review-mode normal --locale ru
reviewmatic check-review --draft <draft-path>
reviewmatic finish-review --draft <draft-path>
```

`--repo-root <checkout>` необязателен: без него используется репозиторий текущей
директории, подходит и подкаталог чекаута.

`start-review` собирает evidence и context, возвращает черновик, снимки файлов
из точных коммитов и шаблон квитанции независимого критика. Дополнительно он
готовит один управляемый review worktree на MR в `<repo>.worktrees/reviewmatic/`:
detached-чекаут точного head MR вне рабочего дерева пользователя. В ответе
`review_worktree` содержит путь к этому дереву, исходный `source_repo_root` и
точные `base_sha`, `start_sha`, `head_sha`, `target_sha` и `target_ref`.
Отсутствующие ревизии загружаются через Git с remote, соответствующего исходному
или целевому проекту MR (любое имя remote, форки поддерживаются); репозиторий не
клонируется, а HEAD, ветка, index, файлы и локальные ветки пользователя остаются
нетронутыми. Код читается из worktree локальным Git; содержимое файлов не
получается из GitLab. Ревью и запуск нативных
сабагентов выполняет текущий агент. Если есть дополнительные профили критиков,
можно выбрать их количество и состав. Если их нет, используются обычные
независимые сабагенты. `critic_count` фиксирует выбранное количество, `critics`
содержит реальные квитанции запусков. Каждый основной кандидат и замечание
критика получает одно решение. Рантайм сам выводит принятые находки, отклонённые
кандидаты, вердикт и привязки артефактов; агент заполняет смысловые оценки,
конкретные исправления, обоснования меток и результаты проверки дискуссий.

Входной пакет сразу содержит `draft_schema_path`, `input_contract` и корректные
примеры полей в `input_examples`, отдельно от финальных артефактов. После
подготовки снимка агент заполняет и записывает общий контекстный пакет
(шаблон `context-package` и `record-package --draft`): цель, утверждения с
источниками, ограничения, прежние решения и вопросы; пакет хранится приватно
вне checkout и привязывается к собранным данным. Запись и чтение пакета не
обращаются к GitLab. Критики стартуют только после записи пакета, получают его
как основной контекст задачи и отвечают в квитанциях на назначенные вопросы
(`question_answers`); при нескольких критиках каждый выбранный критик отвечает
на каждый назначенный вопрос, и ответ одного не закрывает пропуск другого.
При записи рантайм проставляет каждому вопросу дайджест значимого контекста, а
каждый ответ и verification копируют `context_digest` той версии, для которой
они собраны: повторная запись с изменённым вопросом или требованием переносит
затронутые ответы в историю `superseded_question_results` черновика и требует
свежих результатов по затронутому scope, правка только представления
(background) сохраняет их, а поздний ответ с привязкой к прежней версии
отклоняется и не признаёт изменённый вопрос.
Основное ревью затем разбирает каждый ответ
`not_verified` в `question_verifications` черновика, сохраняя исходный ответ.
Запускайте
критика, как только точные снимки и записанный пакет готовы: в фоне параллельно
первичному анализу,
если хост это поддерживает. Resume проверяет и переиспользует снимки без повторной
подготовки. Числового SLA времени ответа нет.

`dispositions[].severity_override` хранит исходную и итоговую severity с причиной,
не изменяя receipt критика. `duplicate_of` указывает на принятую каноническую
находку. Публикация `type=existing_thread` связывает находку с `thread_id`: принятый
thread содержит проверенный фикс, дефект остаётся в вердикте без дублирующей
публикации. Если пользователь сам предложил suggestion/patch, закрытие thread
другим участником не заменяет его подтверждения. Позднее подтверждение привязывается
через `user_confirmation.evidence_note_ids`.

В начале ранбука стоят выведенный вердикт с причиной, блокеры, архитектура и SemVer.
У дефектов указано влияние на слияние, у остальных обсуждений - результат проверки.
Suggestion остаётся в исходном thread при пригодной позиции; иначе новый positioned
thread ссылается на исходный, а исходный получает только краткий ответ о переносе
фикса. Перед каждым патчем показан `patch_reason`. Доступный безопасный bounded
suggestion нельзя заменить патчем.

`recommended_issues` - краткие неблокирующие предложения, не тела issues и не
команды создания: проблема, подтверждение, решение, важность, риск откладывания,
почему вне MR и существующая задача, если известна. Полная подготовка выполняется
отдельно через `task-prepare`; обязательные исправления MR туда не переносятся.

`check-review` работает локально: возвращает пути полей и ошибки, не читает GitLab
заново и не фиксирует решение. Исправьте тот же черновик и повторите проверку.
`resume-review --artifact-root <root>` возвращает его после прерывания без
повторного сбора данных. `finish-review` проверяет черновик, один раз обновляет
полные evidence и context и атомарно сохраняет итоговый план, Markdown и baseline.
Если данные изменились, черновик и предыдущий итоговый план сохраняются; для
изменившегося MR используйте `refresh-review --draft <draft-path>`: находки
сохраняются, пересматривается затронутая область. Изменение только CI возвращает
`refresh_required` с отдельным неизменяемым снимком CI; обновите оценки и текст
в том же черновике без нового ревью кода. Время сбора, проверки и финализации
возвращается отдельно от времени модели и сабагентов. Существующие артефакты v2
и низкоуровневые команды `prepare`/`context`/`template-review` поддерживаются;
не смешивайте два workflow в одном ревью.
Legacy-поле MR `pipeline` и timestamps `latest_build_started_at`/`latest_build_finished_at`
относятся к CI-only evidence. Изменения проверяемого head, метаданных, discussions
или конфликтов остаются существенными: устаревшие оценки переиспользовать нельзя.

Локальные ревью незакоммиченного используют `prepare-local` и `finalize-local`;
`status`, `next` и `assess-mode` показывают прогресс. Каждая команда печатает
компактный JSON и никогда не меняет GitLab или чекаут. Без `--ref` область
проверки — незакоммиченная работа относительно HEAD: staged, unstaged и
неигнорируемые untracked-файлы; явный `--ref <revision>` добавляет коммиты от её
merge base с HEAD и используется ровно так, как она существует локально, без
fetch. Отсутствующий, неоднозначный или не имеющий общей базы `--ref`
останавливает подготовку с конкретной причиной — включая выражения вроде
`dup~0`, когда базовое имя совпадает и с веткой, и с тегом; передавайте одно
полностью квалифицированное refname, — а пустая область возвращает
`empty_scope` вместо снимка. Локальной подготовке не нужны `glab`, сеть, remote
или worktree. Локальное ревью заполняет и записывает тот же общий контекстный
пакет (`record-package --bundle`), привязанный к подготовленному снимку с его
ref сравнения и секциями committed, staged, unstaged и untracked; отчёт при
финализации связывается с записанным пакетом, а возвращённый
`record_command` уже содержит точный путь immutable-снимка. Повторная запись
пакета с изменённым вопросом или требованием переносит ответы отчёта,
собранные для прежней формулировки, в `superseded_question_results` и требует
свежих ответов перед финализацией; ответы и verifications отчёта копируют
`context_digest` вопроса, и финализация отклоняет отсутствующую или
устаревшую привязку, поэтому поздний результат для прежней формулировки не
признаёт изменённый вопрос.

## Интерактивный разбор плана

TUI экспериментальный: его пока не развивают и не проверяют поведенческими
тестами для блокирующей приёмки. Ink, PTY и серверные TUI suites исключены из
основных проверок. Сбор данных, подготовка, repair, refresh, финализация и прямые
команды публикации остаются поддерживаемыми и проверяемыми, включая backend
helpers в `tui/support.js`. `npm test` запускает backend suites и проверки локальных worktrees.

`runbook.md` - второй полноценный интерфейс: прочитайте тело публикации и
скопируйте прямую команду `glab`. TUI выполняет те же операции без shell.

После ревью агент печатает краткий саммари и одну команду:

```bash
reviewmatic plan --artifact-root <root>
```

Запустите её вручную в терминале. По каждому треду видны весь разговор, оценка,
обоснование, ссылка на GitLab и черновик ответа, даже если публикация не
предлагается. Стрелки или `j`/`k` выбирают пункты и прокручивают текст, Page Up/Down
прокручивают длинные списки и разговоры, стрелки влево/вправо переходят между
пунктами. В терминалах с OSC 8 ссылки кликабельны; `o` открывает выбранную
дискуссию в браузере. Enter только открывает пункт и никогда не публикует ответ.

`s` предлагает отправить ответ, `r` - сменить состояние thread после успешного ответа в этой ручной сессии,
`S` - ответ вместе с запланированным
закрытием/переоткрытием. Затем требуется подтверждение `y`. Escape отменяет
подтверждение или возвращает к списку. У пунктов только для чтения нет действий
отправки и редактирования. Клавиша `e` открывает черновик в `$EDITOR`; перед
отправкой план, `runbook.md` и baseline обновляются вместе. Сохранение не отправляет
ответ. `t` переключает ответ/контекст. Во время отправки можно читать и переходить
между пунктами; `z` отменяет локальное ожидание, `q` выходит. При редактировании тела
с патчем его проверенный код, причина и команда должны сохраниться. Новые треды, предложения задач и
лейблы проходят тот же разбор. Саджесты и git-патчи дополнительно предлагают
локальное применение: reviewmatic создаёт отдельный git worktree на точном
reviewed head, показывает diff, а коммит и пуш запрашивает двумя отдельными
подтверждениями.

Ответ и смена состояния находятся в одном `shell`-блоке с поясняющими `#` и `&&`.
Обычные комментарии используют реальный discussion ID и разрешимость из ответа
POST: завершённые обсуждения можно закрыть, вопросы и неисправленные дефекты нельзя.
Прямые блоки для обычных комментариев требуют `jq`. Если ответ отправлен, но смена
состояния не удалась, проверьте GitLab и не повторяйте ответ вслепую.

Одна отправка показывает exit code, вывод и ошибку; состояние меняется только после
успешного ответа.
Нет публикационных locks, квитанций, reservations, срока действия, polling,
автоматических перепроверок или повторов. Результат проверяете в браузере вы и сами
решаете, повторять ли отправку. Таймаут или отмена не отменяет принятый GitLab запрос;
повтор может создать дубль. Ошибка или перезапуск не блокирует следующую попытку.

## Исправить новый финализированный план

```bash
reviewmatic repair-review --artifact-root <root> --kind presentation
reviewmatic check-review --draft <draft-path>
reviewmatic finish-review --draft <draft-path>
```

Заполните `repair.rationale` и `repair.checks`. `presentation` сохраняет смысл и
полный результат фикса, включая режимы файлов. `fix` допускает другой фикс
подтверждённой проблемы после целевой проверки потребителей и тестов, без нового
критика. `decision` меняет выводы и требует новой независимой целевой проверки.
Неясный смысл требует decision repair; нехватка проверок останавливает ремонт без
замены текущего плана и автоматического расширения ревью. Ремонт ничего не публикует.
Основной вариант фикса - suggestions; связанные части задаются через `suggestions`
(`path`, `line`, `body`) и `split_rationale`. Патч требует `patch_reason`; diff
передаётся в `patch`, а `body` содержит только прозу.

После обновления runtime этот же ремонт `presentation` пересоздаёт команды
существующего guided-плана contract-7. Сравните старые и новые тела комментариев,
позиции, находки и квитанции критиков; запишите проверки перед финализацией.
Повторный сбор по сети и полное ревью не требуются. Само обновление не меняет
команды сохранённого плана. Inline-команды теперь передают `position` вложенным
JSON, совместимым с `glab` 1.120.0, вместо неподдерживаемых полей со скобками.

Каждая часть suggestions с пояснением публикуется как самостоятельный комментарий
без общей вводной. Сохраните в ней все необходимые оговорки. Блоки без пояснения
по-прежнему наследуют общую прозу. Ранбук выводит точные дубли проверок один раз.
Проверки thread-блокеров и patch fallback одинаковы для guided-черновиков и
low-level scaffold, даже если старое решение не содержит `blocking_thread_ids`.
Routing-only ответ редактируется как проза, а не как публикация suggestion.
Необязательное поле `routing_response` сохраняет правку при presentation repair,
не меняя общее объяснение и код positioned suggestion. Изменение кода suggestion
по-прежнему требует целевого fix repair.

## Реестр worktree

Созданные worktree записываются в
`$XDG_STATE_HOME/agent-skills/reviewmatic/worktrees.json`; review worktree,
подготовленные `start-review`, — в `review-worktrees.json` рядом. Общий файл
реестра обновляется под короткой блокировкой, поэтому параллельные подготовки
разных MR сохраняют обе записи, и fetch не выполняется под этой блокировкой.
Пути review worktree заканчиваются коротким хешем полной идентичности host,
project и MR, поэтому совпадающие читаемые имена и обрезанные длинные пути
проектов никогда не делят одно дерево. Управляемое дерево старой схемы без
этого хеша не переиспользуется, не перемещается и не удаляется автоматически:
подготовка останавливается с конкретной инструкцией ручного перехода —
сохраните активное ревью и локальные изменения, удалите дерево командом
`git worktree remove`, и следующий запуск заменит устаревшую запись и создаст
путь с хешем. Больше ничего не удаляется автоматически; `reviewmatic worktree
list` печатает реестр применения исправлений с состоянием коммита и пуша по
каждому worktree.

## Контракт совместимости

Существующие планы v2 и квитанции одного критика остаются читаемой историей. Ремонт
доступен только для новых guided-планов контракта 7. Старые охраняемые действия не
исполняются и не мигрируют автоматически; живое прежнее состояние не удаляется. Квитанции
нескольких критиков добавляют необязательное поле `contributors` и требуют
обновлённого рантайма; общая схема и TS-копия проверяются вместе. Canonical JSON
и digest'ы сверяются с Python-референсом в тестах. Пакет не
создаёт состояния на `--help` и `--version`.
